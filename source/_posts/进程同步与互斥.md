**进程同步与互斥**研究的是：多个并发进程**共享资源**、**相互合作**时，如何保证执行结果正确且可复现——不加协调的并发会产生**竞态条件**（结果取决于进程执行的相对次序）。408 对本章的考查集中在：**临界区互斥四准则、软件/硬件实现方法、互斥锁（自旋锁 vs 互斥量）、信号量 P/V 原语、三大应用模板（互斥/同步/前驱）与经典同步问题（生产者-消费者、读者-写者、哲学家进餐、吸烟者）**——选择题爱考"违反了哪条准则""信号量值的含义""P 操作的顺序"，大题几乎必考"用信号量写完整的同步互斥代码"。

## 同步与互斥的基本概念

### 临界资源与临界区

**临界资源（Critical Resource）**：一次**仅允许一个进程**使用的资源，如打印机、共享变量、共享缓冲区。**临界区（Critical Section）**：进程中**访问临界资源的那段代码**。每个进程访问临界资源的代码都分为**四个部分**：

```c
do {
    entry section;       // 进入区：检查临界资源是否可用，可用则"上锁"
    critical section;    // 临界区：实际访问临界资源的代码
    exit section;        // 退出区："解锁"，恢复临界资源的可用标志
    remainder section;   // 剩余区：其余不涉及临界资源的代码
} while (true);
```

### 同步与互斥的定义（重点对比）

| 对比项 | 同步 | 互斥 |
|:---|:---|:---|
| 起因 | **直接制约**：进程**相互合作**，前一个进程的**输出**是后一个进程的**输入** | **间接制约**：进程**竞争临界资源** |
| 要求 | 协调推进顺序——"必须**先做什么，再做什么**" | 同一时刻**只允许一个进程**访问资源 |
| 典型例子 | 生产者-消费者、前驱图任务 | 打印机、共享变量 |
| 信号量做法 | 同步信号量**初值 0**（看资源初值），口诀"**前 V 后 P**" | 互斥信号量 **mutex = 1**，口诀"**进 P 退 V**" |

> **考点**：同步 = 协作关系（"一前一后"），互斥 = 竞争关系（"一次一个"），互斥可看作**特殊的同步**。
> **易错点**：同步关系**每对一个信号量**（互不共用）；互斥则**所有进程共用同一个 mutex**。

### 临界区互斥的四条准则（选择题常考）

| 准则 | 含义 |
|:---|:---|
| **空闲让进** | 临界区**空闲**时，应允许一个请求进入的进程**立即进入** |
| **忙则等待** | 已有进程在临界区时，其他试图进入的进程**必须等待**（互斥的底线） |
| **有限等待** | 等待的进程必须在**有限时间内**能进入（不能"饿死"） |
| **让权等待** | 进不去的进程应**释放 CPU**（阻塞自己），避免忙等空转浪费处理机 |

> **考点**：四条准则缺一不可，选择题常问"某算法违反了哪一条"——违反"忙则等待"（如双标志先检查）是**正确性错误**；只违反"让权等待"（如 Peterson、TSL 忙等）只是效率问题，不算错误。

## 实现互斥的软件方法

### 单标志法

用一个 `turn` 变量表示"当前轮到谁"，谁用完就把使用权让给对方：

```c
int turn = 0;                  // 当前允许进入临界区的进程号，初始只允许 P0
// P0 进程                          // P1 进程
while (turn != 0);                  while (turn != 1);   // 进入区：轮到自己才能进
critical section;                   critical section;    // 临界区
turn = 1;                           turn = 0;            // 退出区：把使用权让给对方
remainder section;                  remainder section;   // 剩余区
```

**缺陷**：`turn` 初始为 0，两进程**必须交替进入**——若 P0 用完后 P1 **暂不申请**，`turn` 停在 1 不变，临界区即使**空闲** P0 也永远进不去：**违背"空闲让进"**（也随之违背有限等待）。

### 双标志先检查法

`flag[i]` 表示进程 i 的进入意愿，**先检查对方意愿，再表明自己的意愿**：

```c
bool flag[2] = {false, false};     // flag[i] = true 表示 Pi 想进入临界区
// P0 进程                          // P1 进程
while (flag[1]);                    while (flag[0]);     // ① 先检查：对方想进就等
flag[0] = true;                     flag[1] = true;      // ② 再表明：自己想进
critical section;                   critical section;    // ③ 临界区
flag[0] = false;                    flag[1] = false;     // ④ 退出区：撤销意愿
```

**缺陷演示（同时进入）**：两进程**几乎同时**执行 ①——都看到对方 `flag = false`、都通过检查，随后**都置自己的 flag = true**，**双双进入临界区**。根因："检查"与"上锁"是**两步、之间可被打断**，不是原子操作——**违背"忙则等待"**。

### 双标志后检查法

把顺序反过来：**先表明意愿，再检查对方**：

```c
// P0 进程                          // P1 进程
flag[0] = true;                     flag[1] = true;      // ① 先表明自己想进
while (flag[1]);                    while (flag[0]);     // ② 再检查对方
critical section;                   critical section;    // ③ 临界区
flag[0] = false;                    flag[1] = false;     // ④ 退出区
```

**缺陷演示（都进不去）**：两进程**都先置 flag = true**，再互相检查时**都发现对方想进**——都卡在 `while` 上空转，临界区明明空闲却**谁都进不去**：**违背"空闲让进"**；且两进程**互等**、可能长期得不到服务，**也违背"有限等待"**（饥饿）。

### Peterson 算法

思想 = "**表达意愿 + 主动谦让**"：先置自己的 flag（愿进），再把 turn 让给对方，最后同时检查两个条件：

```c
bool flag[2] = {false, false};     // 意愿数组：flag[i] = true 表示 Pi 想进入
int turn = 0;                      // 谦让变量：当前把优先权让给谁
// P0 进程                                // P1 进程
flag[0] = true;  turn = 1;                flag[1] = true;  turn = 0;     // ① 表达意愿 + 让给对方
while (flag[1] && turn == 1);             while (flag[0] && turn == 0);  // ② 对方想进且轮到对方才等
critical section;                         critical section;              // ③ 临界区
flag[0] = false;                          flag[1] = false;               // ④ 退出区：撤销意愿
```

- **空闲让进**：对方不愿进（`flag[j] = false`）或优先权在自己手里（`turn == i`）→ 直接进入；
- **忙则等待**：双方同时申请时 `turn` 只有一个值——**后写 turn 的一方谦让**（turn 被后写者覆盖，先写者进入），**不可能同时进入，也不会互等死锁**；
- **有限等待**：等待方最多等对方**用完一次**（对方退出置 `flag[j] = false`，循环条件失效）；**让权等待**：**不满足**（`while` 忙等）。

> **考点**：Peterson 与"双标志后检查"的本质区别就在 `turn`——turn 只能赋一个值，保证"必有一方退出竞争"；但它**只适用于两个进程**且**忙等**，实际系统采用硬件方法。

**软件四法对比**：

| 方法 | 能否实现互斥 | 是否忙等 | 满足让权等待 | 主要问题（违反的准则） |
|:---|:---|:---|:---|:---|
| **单标志法** | 能（强制交替） | 是 | 否 | 必须**交替**进入：对方不申请时自己永远进不去——违背**空闲让进** |
| **双标志先检查** | **不能** | 是 | 否 | 检查与上锁之间可被打断，**双方同时进入**——违背**忙则等待** |
| **双标志后检查** | **不能** | 是 | 否 | 双方先上锁再互查，**谁都进不去**——违背**空闲让进**、**有限等待** |
| **Peterson** | 能 | 是 | 否 | 满足前三条准则；**忙等**、仅限**两个进程** |

## 实现互斥的硬件方法

### 中断屏蔽（关中断）

进入临界区前**关中断**，出临界区再**开中断**——关中断期间不响应任何中断、不发生进程切换，临界区代码得以"原子"执行（与**原语**的实现思想相同）：

```c
关中断;                 // 关中断后 CPU 不响应中断 → 不会发生进程切换
critical section;       // 这段代码一定"一口气"执行完
开中断;                 // 恢复中断响应
```

- **优点**：简单、高效；**缺点**：**不适用于多处理机**（关中断只对本 CPU 生效，其他 CPU 仍可进入同一临界区）；**只适用于内核进程**（开/关中断是**特权指令**，用户进程无权执行）；关中断期间无法响应时钟、I/O，滥用危险。

### TestAndSet 指令（TS/TSL）

一条硬件**原子指令**：**读出旧值的同时把锁置为 true**——把软件方法里可被打断的"检查 + 上锁"两步合并为不可分割的一步：

```c
bool TestAndSet(bool *lock) {    // 硬件保证原子执行
    bool old = *lock;            // ① 读出 lock 的旧值
    *lock = true;                // ② 无论是否已上锁，都置为 true（上锁）
    return old;                  // ③ 返回旧值：false 表示"原来没锁，我抢到了"
}
bool lock = false;               // 共享锁变量：false = 空闲
while (TestAndSet(&lock));       // 进入区：返回 true 说明别人已上锁，忙等
critical section;                // 临界区
lock = false;                    // 退出区：解锁
```

### Swap 指令（XCHG）

硬件**原子交换指令**，逻辑上与 TSL 无本质区别——用 `old` 换出 lock 的旧值，再检查 `old`：

```c
void Swap(bool *a, bool *b) {    // 硬件保证原子执行的交换指令
    bool temp = *a;  *a = *b;  *b = temp;
}
bool old = true;                 // 暂存 lock 旧值的变量，初始 true（假设已上锁）
while (old == true)
    Swap(&lock, &old);           // 把 lock 的旧值换到 old，同时把 true 写入 lock
critical section;                // old 换得 false → 原来未上锁，成功进入；否则继续循环忙等
lock = false;                    // 退出区：解锁
```

**硬件三法对比**：

| 方法 | 能否互斥 | 是否忙等 | 适用范围 | 优点 | 缺点 |
|:---|:---|:---|:---|:---|:---|
| **中断屏蔽** | 能 | 否（根本不会被切换） | **单处理机 + 内核进程** | 简单高效 | 特权指令用户不可用；**多处理机失效** |
| **TS/TSL** | 能 | **是**（自旋） | 单核、**多核均可** | 简单、无需严谨的逻辑推敲、支持多处理机 | 忙等，违背**让权等待**；不保证先来先到，可能饥饿 |
| **Swap** | 能 | **是**（自旋） | 单核、**多核均可** | 同 TSL | 同 TSL |

> **考点**：硬件方法把"检查 + 上锁"合并为**一条原子指令**，从根本上消除软件方法"两步之间被打断"的漏洞；但 TS/Swap 是"抢锁"而非"排队"——**都忙等**（不满足让权等待）。TSL/Swap **适用于多处理机**，这是与中断屏蔽最常对比的一点。

## 互斥锁

**互斥锁（Mutex Lock）**：最简单的同步工具——一个锁变量 + 两个**原子**操作 `acquire`（上锁）/ `release`（解锁）：

```c
bool available = true;      // 锁变量：true = 可用（未上锁），false = 已被占用
acquire() {                 // 上锁：进入临界区前调用
    while (!available);     // 锁被占用 → 原地循环等待（忙等）
    available = false;      // 拿到锁，置为占用
}
release() {                 // 解锁：退出临界区后调用
    available = true;       // 释放锁
}
```

- `acquire`/`release` 的**原子性**由硬件指令（TSL、Swap 等）保证；**自旋锁（Spin Lock）**：`acquire` 失败时**原地循环等待（忙等）**的互斥锁；**互斥量（基本锁）**：拿不到锁就**阻塞**自己、进入等待队列，由操作系统在解锁时唤醒（让权等待）。

**自旋锁 vs 互斥锁**：

| 对比项 | 自旋锁（忙等） | 互斥锁/互斥量（阻塞） |
|:---|:---|:---|
| 拿不到锁时 | **原地空循环**反复试探 | **阻塞自己**，挂入等待队列 |
| 上下文切换 | **无**（不进内核、不切换） | **有**（保存/恢复现场、用户态与内核态切换，开销大） |
| 是否满足让权等待 | **不满足** | **满足** |
| CPU 消耗 | 空转**占用 CPU** | 让出 CPU，但切换本身有开销 |
| 适用场景 | **多核**、临界区**短**、持锁时间短 | 临界区**长**、持锁时间长、单处理机 |

> **考点**：自旋锁忙等但**无切换开销**，临界区很短时反而更高效；**单处理机不适合自旋**——自旋进程占着唯一的 CPU，持锁进程无法被调度、永远释放不了锁。
> **易错点**：自旋锁只是不满足"让权等待"这一建议性准则，不等于错误实现。

## 信号量机制

**信号量（Semaphore）**= 一个**整型变量 S** + 两个**原子**操作：**P（wait，申请资源）**与 **V（signal，释放资源）**。它是 408 大题的核心工具。

### 整型信号量（忙等实现）

```c
int S = 1;                  // S 表示当前可用资源数（以 1 台打印机为例）
void wait(int S) {          // P 原语（相当于进入区）：申请一个资源
    while (S <= 0);         // 没有可用资源就原地循环——忙等
    S = S - 1;              // 有资源，占用一个
}
void signal(int S) {        // V 原语（相当于退出区）：释放一个资源
    S = S + 1;
}   // 缺点：不满足"让权等待"——无资源时进程在 while (S <= 0); 处忙等空转占 CPU
```

### 记录型信号量（重点，让权等待实现）

数据结构 = **剩余资源数 value + 等待队列 L**；P 不够就**阻塞自己**，V 则**唤醒一个**等待者：

```c
typedef struct {                // 记录型信号量：value = 剩余资源数（可为负）
    struct process *L;          // L = 等待该资源的进程队列
} semaphore;
void P(semaphore S) {           // wait 原语：申请一个资源
    S.value--;                  // 先减 1
    if (S.value < 0)            // 减完 < 0：资源已用尽
        block(S.L);             // 自我阻塞，挂入 S 的等待队列（让权等待）
}
void V(semaphore S) {           // signal 原语：释放一个资源
    S.value++;                  // 先加 1
    if (S.value <= 0)           // 加完仍 ≤ 0：说明还有进程在排队
        wakeup(S.L);            // 从等待队列唤醒一个进程
}
```

**value 的取值含义（必考）**：$S.value > 0$ 表示还有 $S.value$ 个**可用资源**；$S.value = 0$ 表示资源刚好用完、暂无人等待；$S.value < 0$ 时**绝对值 = 等待队列中的进程数**（如 $S.value = -3$ 即已有 3 个进程在排队）。

> **考点**：P 操作 = **申请**资源（可能阻塞**自己**），V 操作 = **释放**资源（可能唤醒**别人**）；P/V 都是**原语**，执行期间不可中断。口诀：P 减 1 后**小于 0** 才阻塞，V 加 1 后**不大于 0** 就唤醒。
> **易错点**：整型信号量是"**先检查后减**"（忙等）；记录型是"**先减后判断**"（阻塞）——顺序不同，性质不同。

### 用信号量实现互斥（模板）

```c
semaphore mutex = 1;        // 互斥信号量：初值 = 1（临界资源只有 1 个）
P(mutex);                   // 进入区：申请临界资源
critical section;           // 临界区
V(mutex);                   // 退出区：释放临界资源
remainder section;          // 剩余区
```

- **P/V 必须成对出现**：缺 `P(mutex)` → 互斥失效；缺 `V(mutex)` → 资源永不释放、等待进程永远阻塞；**任何进程**都可对同一 mutex 执行 P/V（进临界区者负责解锁），不区分"谁申请谁释放"。

### 用信号量实现同步（模板）

```c
semaphore S = 0;            // 同步信号量：初值 = 0（"前操作"尚未发生）
/* 进程 P1 —— 必须先执行的一方 */
code1;  V(S);               // 前操作完成后发信号："code1 已经做完"
/* 进程 P2 —— 必须后执行的一方 */
P(S);   code2;              // 没等到信号就一直阻塞，保证 code1 先于 code2
```

口诀：**"前 V 后 P"**——先做的事之后 V，后做的事之前 P；同步信号量**初值 0**；有几种"先后关系"就设几个同步信号量。

### 用信号量实现前驱关系（模板）

每一对前驱关系都是一个同步问题：**每条边设一个信号量（初值 0）**，前驱代码完成后对其**出边 V**，后继代码开始前对其**入边 P**：

![前驱图：每条边设一个初值为 0 的同步信号量，前 V 后 P](/blog/images/OS第2章 进程管理.assets/前驱图-信号量设计.png)

```c
semaphore a=0, b=0, c=0, d=0, e=0, f=0, g=0;    // 每条前驱边一个信号量，初值均为 0
P1() { S1; V(a); V(b); }          // S1 完成后，通知 S2（a）、S3（b）
P2() { P(a); S2; V(c); V(d); }    // 等 S1 完成；S2 完成后通知 S4（c）、S5（d）
P3() { P(b); S3; V(g); }          // 等 S1 完成；S3 完成后通知 S6（g）
P4() { P(c); S4; V(e); }          // 等 S2 完成；S4 完成后通知 S6（e）
P5() { P(d); S5; V(f); }          // 等 S2 完成；S5 完成后通知 S6（f）
P6() { P(e); P(f); P(g); S6; }    // 等 S4、S5、S3 全部完成后才能执行 S6
```

## 经典同步问题

**P/V 大题通用解题三步骤**：① **关系分析**——找出各进程，分析**同步、互斥关系**；② **整理思路**——按操作流程确定 P、V 的**大致顺序**（同步"前 V 后 P"，互斥"进 P 退 V"）；③ **设置信号量**——互斥信号量初值一般为 1，**同步信号量初值 = 对应资源的初始数量**。

### 生产者-消费者问题

**问题与分析**：生产者生产产品放入容量为 $n$ 的**有界缓冲区**，消费者从中取产品消费。三类关系：缓冲区**满**时生产者必须等待（同步）、缓冲区**空**时消费者必须等待（同步）、缓冲区是临界资源须**互斥**存/取。**信号量设计（初值理由）**：`mutex = 1`（互斥访问缓冲区，一次只允许一个进程存/取）；`empty = n`（空缓冲单元数，初始 = 缓冲区容量 n）；`full = 0`（产品单元数，初始一个产品也没有）。

![生产者-消费者：缓冲区满时生产者等待、缓冲区空时消费者等待](/blog/images/OS第2章 进程管理.assets/生产者消费者-缓冲区.png)

```c
semaphore mutex = 1;    // 互斥：一次只允许一个进程存/取缓冲区
semaphore empty = n;    // 同步：空缓冲单元数（初始 = n）
semaphore full  = 0;    // 同步：产品单元数（初始 = 0）
producer() {                      consumer() {
    while (1) {                       while (1) {
        生产一个产品;                     P(full);      // ① 先申请一个产品（空则阻塞）
        P(empty);   // ① 申请空单元       P(mutex);     // ② 再申请缓冲区
        P(mutex);   // ② 申请缓冲区       从缓冲区取出产品;
        把产品放入缓冲区;                 V(mutex);     // ③ 释放缓冲区
        V(mutex);   // ③ 释放缓冲区       V(empty);     // ④ 空单元数加 1
        V(full);    // ④ 产品数加 1       消费产品;
    }                                 }
}                                 }
```

> **考点（必考）**：**P 操作的顺序不能颠倒**——若生产者先 `P(mutex)` 再 `P(empty)`，缓冲区满时生产者**抱着 mutex 阻塞**在 empty 上，消费者 `P(mutex)` 拿不到锁、无法取走产品 → **死锁**；消费者侧 `full` 与 `mutex` 的顺序同理（empty/mutex 与 full/mutex 两处都易错）。**V 的顺序可以交换**，不影响正确性。
> **易错点**：互斥 `P(mutex)` 必须夹在**中间**——同步 P 在外、互斥 P 在内；初值 **mutex=1、empty=n、full=0**。这种"互斥与同步嵌套、P 顺序不当"的死锁，详见姊妹文章《死锁》。

### 多生产者-多消费者问题（水果盘）

**问题与分析**：桌上一个**盘子，每次只能放一个水果**。爸爸专放**苹果**、妈妈专放**橘子**；女儿专吃苹果、儿子专吃橘子。爸爸与女儿、妈妈与儿子分别是**同步**关系（放完通知对应子女）；盘子容量为 1，`plate` **兼做互斥**。信号量设计：`plate = 1`（盘子空位数）、`apple = 0`、`orange = 0`（盘中对应水果数，**按种类区分，谁需要谁 P**）。

```c
semaphore plate  = 1;   // 盘子空位数（容量为 1，兼做互斥）
semaphore apple  = 0;   // 盘中苹果数
semaphore orange = 0;   // 盘中橘子数
father() {                      mother() {
    while (1) {                     while (1) {
        准备一个苹果;                   准备一个橘子;
        P(plate);   // 盘空才能放       P(plate);    // 盘空才能放
        放苹果入盘;                     放橘子入盘;
        V(apple);   // 通知女儿         V(orange);   // 通知儿子
    }                               }
}
daughter() {                    son() {
    while (1) {                     while (1) {
        P(apple);   // 有苹果才取       P(orange);   // 有橘子才取
        取出苹果;                       取出橘子;
        V(plate);   // 取走才释放       V(plate);    // 取走才释放
        吃苹果;                         吃橘子;
    }                               }
}                               }
```

> **考点**：生产者放完 **V 对应水果信号量**，消费者**取走才 V(plate)**。盘子容量为 1 时 `plate` 兼当互斥信号量；若容量大于 1，必须**另加 mutex=1** 保护"放/取"过程（此时 P(mutex) 与 P(plate) 的顺序同样不能颠倒）。

### 读者-写者问题

**问题与分析**：允许多个读者**同时**读文件；写者必须**独占**访问（写时不允许任何读者或其他写者）。写者与写者、写者与读者之间**互斥**，读者与读者**共享**。关键技巧：用 `count` 记录读者数，**第一个读者负责上锁、最后一个读者负责解锁**——读者之间"共享锁"。信号量设计：`rw = 1`（读写互斥锁，写者直接 P/V）；`count = 0`（正在读的读者数，共享变量**本身也是临界资源**，必须用 `mutex = 1` 保护）。

```c
Reader:                               Writer:
while (1) {                           while (1) {
  P(mutex);                             P(rw);     // 写者直接独占读写锁
  if (count == 0)                       write();
      P(rw);    // 第 1 个读者上锁      V(rw);
  count++;                            }
  V(mutex);
  read();    // 多读者可同时读
  P(mutex);
  count--;
  if (count == 0)
      V(rw);    // 最后 1 个读者解锁
  V(mutex);
}
```

> **考点**：`count` 必须用 mutex 保护——`count++` 不是原子操作，两个读者并发修改会互相覆盖，导致计数错乱、提前 `V(rw)`，**破坏读写互斥**；`count == 0` 的判断也必须放在 mutex 临界区内。
> **易错点**：读优先策略下读者源源不断时**写者可能饥饿**；改进为"写优先/读写公平"：再加一个信号量 `w = 1`，写者整个写期间持有 w，读者申请 rw 的关口也要先过 w——使写者到达后后续读者排队，思想了解即可。

### 哲学家进餐问题

**问题与死锁分析**：5 位哲学家围坐圆桌，5 根筷子分放每人左右；每人需**同时拿到左右两根筷子**才能进餐，用完放回。**错误解法**：所有人都"先拿左筷、再拿右筷"——若 5 人**同时**执行第一个 P、各拿到左筷，再申请右筷时**互相等待**，形成**循环等待**：谁都无法进餐、也无法释放筷子（死锁）。**错误代码**：

```c
semaphore chopstick[5] = {1, 1, 1, 1, 1};   // 5 根筷子，每根一个初值为 1 的信号量
// 第 i 号哲学家的进程（错误：可能死锁）
while (1) {
    P(chopstick[i]);              // 先拿左筷子
    P(chopstick[(i + 1) % 5]);    // 再拿右筷子
    进餐;
    V(chopstick[i]);              // 放下左筷子
    V(chopstick[(i + 1) % 5]);    // 放下右筷子
    思考;
}
```

**防止死锁的三种策略**：

| 策略 | 做法 | 破坏了什么 |
|:---|:---|:---|
| ① **限流**：最多 4 人同时拿筷子 | 加信号量 `room = 4`，进餐前 P(room)、完毕 V(room) | 4 人争 5 根筷子，**必有一人能拿到两根**，进餐后释放，不会循环等待 |
| ② **一次性拿齐**（原子拿筷） | 用 `mutex` 把"拿左 + 拿右"包成**临界区** | 不出现"各持一根互等"的中间状态（破坏请求与保持） |
| ③ **奇偶规则** | **奇数号先拿左筷、偶数号先拿右筷** | 相邻哲学家先争**同一根**筷子，必有一人先拿到，破坏循环等待 |

**策略② 的完整代码**：

```c
semaphore chopstick[5] = {1, 1, 1, 1, 1};   // 5 根筷子
semaphore mutex = 1;                         // 保护"拿筷子"这一过程
// 第 i 号哲学家的进程
while (1) {
    P(mutex);                  // 进入"拿筷子"临界区：拿筷动作不可被打断
    P(chopstick[i]);           // 拿左筷
    P(chopstick[(i + 1) % 5]); // 拿右筷
    V(mutex);                  // 两根都拿到后立刻退出临界区
    进餐;
    V(chopstick[i]);  V(chopstick[(i + 1) % 5]);   // 放下两根筷子
    思考;
}
```

**策略③ 进入区写法**：奇数号 `P(chopstick[i]); P(chopstick[(i+1)%5]);`（先左后右），偶数号 `P(chopstick[(i+1)%5]); P(chopstick[i]);`（先右后左），放筷顺序任意。

> **考点**：策略②中 `P(mutex)` 必须在两个 `P(chopstick)` **之前**（先整体排队，再拿筷）；三种策略对应"限流、一次性分配、顺序请求"，与《死锁》一章的预防思想一一对应。

### 吸烟者问题

**问题与分析**：三个抽烟者各自**无限**拥有烟草、纸、胶水中的一种，卷一支烟需要**三种材料**；两个供应者**轮流**每次提供三种材料中的**两种**（随机组合），抽完一支烟的抽烟者**发信号通知供应者**，供应者才继续提供下一组。关系是**双向同步**：供应者提供组合 → 对应抽烟者取用（单向）；抽烟者抽完 → 通知供应者（反向），缺一不可。信号量设计：每种材料组合设一个信号量、**初值均为 0**（一组材料恰好只有一个"有缘人"——拥有其余两种材料者）；`finish = 0` 保证"抽完才放下一组"。

**组合对应关系**：提供"烟草+纸" → 有胶水者（offer1）；提供"烟草+胶水" → 有纸者（offer2）；提供"胶水+纸" → 有烟草者（offer3）。

```c
semaphore offer1 = 0;   // "烟草 + 纸"组合（给有胶水者）
semaphore offer2 = 0;   // "烟草 + 胶水"组合（给有纸者）
semaphore offer3 = 0;   // "胶水 + 纸"组合（给有烟草者）
semaphore finish = 0;   // "一支烟抽完"的信号量
processP1() {                          // 供应者进程（两个供应者轮流提供）
    while (1) {
        random = random() % 3;         // 随机产生 0、1、2 三种组合之一
        if (random == 0)      V(offer1);   // 提供 烟草+纸   → 有胶水者 P4
        else if (random == 1) V(offer2);   // 提供 烟草+胶水 → 有纸者 P3
        else                  V(offer3);   // 提供 胶水+纸   → 有烟草者 P2
        P(finish);                     // 等抽烟者抽完，才提供下一组
    }
}
processP2() {                  processP3() {                  processP4() {
    while (1) {                    while (1) {                    while (1) {
        P(offer3);                     P(offer2);                     P(offer1);
        卷烟抽掉;  // 缺纸+胶水         卷烟抽掉;  // 缺烟草+胶水       卷烟抽掉;  // 缺烟草+纸
        V(finish);                     V(finish);                     V(finish);
    }                              }                              }
}                              }                              }
```

> **考点**：**双向同步**——供应者 `V(offer_i)` 与抽烟者 `P(offer_i)` 一个方向，抽烟者 `V(finish)` 与供应者 `P(finish)` 反方向，**两个方向都不能省**；**不需要 mutex**：桌上每次只放一套材料，`finish` 已保证"抽完才放下一轮"，不会同时放/取。本题是 **2021 年 408 统考大题原型**。

## 高频考点速记

| 考点 | 记忆 |
|:---|:---|
| 临界资源与临界区 | 一次仅一个进程使用的资源；访问它的代码分**进入区、临界区、退出区、剩余区** |
| 同步 vs 互斥 | 同步 = 直接制约（协作，"前 V 后 P"，初值 0）；互斥 = 间接制约（竞争，"进 P 退 V"，初值 1） |
| 四准则 | **空闲让进、忙则等待、有限等待、让权等待**；违反"忙则等待"是正确性错误，忙等只违反让权等待 |
| 软件四法 | 单标志：必须交替，违背**空闲让进**；先检查：同时进入，违背**忙则等待**；后检查：互等进不去，违背**空闲让进 + 有限等待**；Peterson：意愿 flag + 谦让 turn，**后写 turn 者谦让**，满足前三准则仍忙等，仅两进程 |
| 中断屏蔽 | 关中断保护临界区；**特权指令**（仅内核进程可用）；**多处理机失效** |
| TS/TSL 与 Swap | 原子指令"读旧值 + 上锁"一步完成；适用**多处理机**；**都忙等**（违背让权等待） |
| 自旋锁 vs 互斥锁 | 自旋：忙等、**无切换开销**、适合多核短临界区；互斥量：阻塞让权、适合长临界区、单处理机 |
| 信号量 value | 正值 = **可用资源数**；负值**绝对值 = 等待进程数**；0 = 资源用完无人等 |
| P/V 原语 | P 减 1、**小于 0 阻塞自己**；V 加 1、**不大于 0 唤醒一个**；都是原语，P 申请、V 释放 |
| 整型 vs 记录型 | 整型"先检查后减"忙等；记录型 value + 等待队列，"先减后判断"阻塞（让权等待） |
| 三大模板 | 互斥：mutex=1 进 P 退 V；同步：S=0 前 V 后 P；前驱：**每边一个信号量、初值 0** |
| 生产者-消费者 | mutex=1、empty=n、full=0；**P 顺序不能颠倒**（empty 与 full 的 P 都须在 P(mutex) 前），否则死锁；V 顺序可换 |
| 读者-写者 | count 计数 + mutex 保护；**第一个读者 P(rw)、最后一个 V(rw)**；读优先写者饥饿；写优先再加 w=1 |
| 哲学家进餐 | 5 人同拿左筷 → 循环等待死锁；解法：**room=4 限流 / mutex 原子拿齐 / 奇偶号换手** |
| 吸烟者问题 | 每种材料组合一个信号量（初值 0）+ finish **双向同步**；无需 mutex；2021 统考大题原型 |
