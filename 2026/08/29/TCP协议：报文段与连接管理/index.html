TCP协议：报文段与连接管理

2026-08-29
  • 计算机网络

TCP（Transmission Control Protocol，传输控制协议）是面向连接的可靠传输协议：它把应用交来的数据看成无边界的字节流，给每个字节编号，用序号 + 确认 + 重传保证可靠交付。408 对本部分的考查集中在两块：TCP 报文段首部字段（逐个含义）与连接管理（三次握手、四次挥手、状态转换、序号消耗规则）。可靠传输/流量控制/拥塞控制的机制细节见另文。

TCP 的特点

特点 说明
面向连接 传送数据前必须先三次握手建立连接，用完四次挥手释放；连接是”虚连接”（两端维护状态），不是物理电路
点对点 每条 TCP 连接只有两个端点（两个套接字），不支持一对多/多播（UDP 才可以）
可靠交付 保证无差错、不丢失、不重复且按序到达
全双工 双方都可同时发送与接收，两端都设有发送缓存和接收缓存
面向字节流 把应用交付的数据看作无边界的字节流，按字节编号（不是按报文段编号）

发送缓存与接收缓存

TCP 的全双工通信依靠两端各一对缓存实现：

  • 发送缓存：暂存 ① 已发送但尚未确认的数据（可能要重传）；② 应用交来、待发送的数据
  • 接收缓存：暂存 ① 按序到达但尚未被应用进程读取的数据；② 未按序到达的数据（等缺口补齐后再整体上交）
  • 应用进程不必等整个报文到齐才读——TCP 把字节流凑够一批才交付，写入多少与读出多少可以不等

考点：TCP 五大特点——面向连接、点对点（两个套接字端点）、可靠交付、全双工、面向字节流。
易错点：可靠 = 无差错、不丢失、不重复、有序四项都要；”按字节编号”不是”按报文段编号”，这是后面理解序号/确认号的基础。

TCP 报文段的首部格式

TCP 报文段 = 首部 + 数据。首部固定 20B，加选项最多 60B：

逐个字段说明：

字段 位数 说明
源端口 / 目的端口 各 16 标识收发双方的应用进程
序号 seq 32 本报文段数据部分第一个字节在字节流中的编号（按字节编号）
确认号 ack 32 期望收到对方下一个字节的序号，即已收到的最后一个字节序号 + 1；对该号之前的所有字节累计确认
数据偏移 4 首部长度，以 4B 为单位，取值 5~15 → 首部 20~60B
保留 6 置 0 备用
URG（紧急） 1 =1 表示紧急数据插队优先发送，配合紧急指针（指出紧急数据末尾）使用
ACK（确认） 1 =1 时确认号有效；连接建立后所有报文段 ACK 恒为 1
PSH（推送） 1 =1 要求接收方尽快交付应用层，不等接收缓存填满
RST（复位） 1 =1 表示出现严重差错必须释放连接再重建，也可用于拒绝连接
SYN（同步） 1 =1 表示请求建立连接、同步初始序号；占 1 个序号
FIN（终止） 1 =1 表示数据发完、请求释放连接；占 1 个序号
窗口 16 指己方接收窗口 rwnd——还能接收多少字节，发给对方作流量控制
校验和 16 校验首部 + 数据，计算时也要加 12B 伪首部（协议字段 = 6，不是 UDP 的 17）
紧急指针 16 URG=1 时有效，指出紧急数据末尾在本段中的位置
选项 0~40B 如 MSS（最大报文段长度）；首部须填充为 4B 的整数倍

考点：确认号 = 收到的最后一个字节的序号 + 1；SYN 和 FIN 即使不携带数据也各占一个序号；数据偏移以 4B 为单位（与 IP 首部长度同理）。
易错点：序号是字节编号；TCP 校验和必须计算（UDP 在 IPv4 下可选），且同样加伪首部；窗口字段通告的是自己的接收能力，不是发送能力。

TCP 连接建立：三次握手

设客户端选择的初始序号为 x，服务器选择的初始序号为 y：

各报文明细与状态变化：

步骤 方向 关键字段 含义
① 客户 → 服务器 SYN=1, seq=x（不携带数据） 请求建立连接，同步客户初始序号
② 服务器 → 客户 SYN=1, ACK=1, seq=y, ack=x+1 同意建连，同步服务器初始序号并确认 x
③ 客户 → 服务器 ACK=1, seq=x+1, ack=y+1 确认服务器的 SYN，此报文可携带数据
主机 状态序列
客户端 CLOSED → SYN_SENT →（收到②）→ ESTABLISHED
服务器 CLOSED → LISTEN →（收到①）→ SYN_RCVD →（收到③）→ ESTABLISHED

序号消耗规则：

  • SYN 报文段占 1 个序号（不携带数据也占）→ ② 的确认号是 x+1 而不是 x
  • 单纯 ACK 不占序号 → ③ 之后客户发数据时，第一个数据字节的序号仍是 x+1
  • FIN 同样占 1 个序号（释放连接时同理）

为什么是三次握手（两个原因）：

  1. 防止”已失效的连接请求报文段”突然又传到服务器：客户发出的第一个 SYN 若在网络中滞留很久，客户超时后重发并正常建连；当这个过期 SYN 迟到时，若只有两次握手，服务器回个确认就”建立”了一个无人使用的连接，白白占用资源等待数据。三次握手下，客户对过期请求不发第三次确认，服务器收不到第三次握手便作废该连接。
  2. 同步双方的初始序号：x 和 y 都必须被对方确认——② 确认了 x，③ 确认了 y。两次握手无法让服务器确认客户的确认，初始序号 y 得不到保证。

考点：三次握手中只有 SYN 占序号、纯 ACK 不占；每个握手报文的 seq/ack 要能自己推出来。
易错点：前两次握手不能携带数据，第三次握手可以捎带数据（若携带，数据第一个字节序号就是 x+1）。

半连接与 SYN 洪泛攻击

  • 服务器收到 SYN、回送 SYN+ACK 后进入 SYN_RCVD——连接尚未完全建立，称为半连接，存放在服务器的半连接队列中，等待第三次握手到达
  • SYN 洪泛攻击：攻击者伪造大量 SYN 报文却不回第三次握手，把半连接队列占满，服务器无法为正常用户建立连接
  • 防御——SYN Cookie：服务器收到 SYN 时不分配缓存资源，把连接信息编码进 SYN+ACK 的初始序号；收到第三次握手时验证通过才分配资源

考点：SYN_RCVD 状态 = 半连接；SYN 洪泛攻击攻击的是服务器的半连接队列，经典防御是 SYN Cookie。

TCP 连接释放：四次挥手

设 A（主动关闭方）已把数据发送到序号 u−1 结束，B 在半关闭期间没有再发数据：

步骤 方向 关键字段 说明
① A → B FIN=1, seq=u A 请求释放（A→B 方向），FIN 占序号 u；A 进入 FIN_WAIT_1
② B → A ACK=1, seq=v, ack=u+1 B 确认 A 的 FIN；A 进入 FIN_WAIT_2（半关闭）
③ B → A FIN=1, ACK=1, seq=w, ack=u+1 B 数据发完后也请求释放；B 进入 LAST_ACK
④ A → B ACK=1, seq=u+1, ack=w+1 A 确认 B 的 FIN，进入 TIME_WAIT 等 2MSL；B 收到后 CLOSED

seq/ack 推演要点：

  • ② 的 ack = u+1：u 是 A 的 FIN 序号，FIN 占 1 个序号，确认号必须越过它
  • ③ 的 ack 仍是 u+1：B 无新数据需要确认；若 B 无数据要发，则 w = v（③ 与 ② 的序号相同）
  • ④ 的 ack = w+1：w 是 B 的 FIN 序号，同样占 1 个序号
  • ④ 的 seq = u+1：A 自己的 FIN 占了序号 u，A 的下一个报文从 u+1 起

半关闭（Half-close）：步骤 ①② 之后，A→B 方向已关闭（A 不再发送数据，但仍能接收），而 B→A 方向仍可继续发送数据——A 停在 FIN_WAIT_2 继续收 B 的数据并确认，直到 B 也发 FIN。这就是挥手要四次的根源。

TIME_WAIT 为什么要等 2MSL（MSL = 最长报文段寿命）：

  1. 保证最后的 ACK 能够到达 B：若 ④ 丢失，B 会超时重传 FIN，A 处于 TIME_WAIT 仍可再回 ACK；若 A 直接 CLOSED，B 将无法正常关闭。
  2. 让本连接产生的所有报文段在网络中消逝：等满 2MSL，旧报文全部失效，避免”旧连接的报文”窜入此后用相同端口号建立的新连接。

考点：TIME_WAIT 出现在主动关闭方；2MSL 的来历 = 最后 ACK 的一次传输时间 + 若丢失则 B 重传 FIN 再确认一次的时间。
易错点：若最后 ACK 丢失，B 重传的是 FIN（不是 ACK）；被动关闭方没有 TIME_WAIT，从 LAST_ACK 直接到 CLOSED。

“三次握手”与”四次挥手”的辨析：

问题 答案
握手为什么能”三次”？ 第二次握手中服务器的 SYN 与 ACK 合并为一个报文段——服务器无需等待任何条件即可同步
挥手为什么是”四次”？ B 收到 FIN 时可能还有数据没发完，必须先回 ACK（进入半关闭），数据发完后再发 FIN——ACK 与 FIN 不能总合并
挥手能否”三次”？ 若 B 恰好无数据可发，② 的 ACK 与 ③ 的 FIN 可以合并为一个报文段，但标准流程仍按四次作答

连接各阶段状态一览

状态 出现方 含义
LISTEN 服务器 等待连接请求
SYN_SENT 客户端 已发 SYN，等待服务器确认
SYN_RCVD 服务器 收到 SYN，已回 SYN+ACK
ESTABLISHED 双方 连接建立，可传输数据
FIN_WAIT_1 主动关闭方 已发 FIN，等待确认
FIN_WAIT_2 主动关闭方 半关闭：本方向已关，仍接收对方数据
CLOSE_WAIT 被动关闭方 已确认对方 FIN，等本方应用决定关闭
LAST_ACK 被动关闭方 已发 FIN，等最后一次 ACK
TIME_WAIT 主动关闭方 已回最后 ACK，等 2MSL 再 CLOSED
CLOSED 双方 连接完全关闭

考点：主动关闭方经历 FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT；被动关闭方经历 CLOSE_WAIT → LAST_ACK——看状态即可判断谁先发起的关闭。

典型例题

例题 1：三次握手的序号与确认号推演

题目：主机 A 与服务器 B 建立 TCP 连接，A 选择的初始序号 x = 1000，B 选择的初始序号 y = 5000。写出三次握手各报文段的 seq 与 ack，并指出握手完成后 A 发送的第一个数据字节序号。

报文 方向 标志位 seq ack
① A → B SYN=1 1000 —（SYN=1 时 ack 无效）
② B → A SYN=1, ACK=1 5000 1001
③ A → B ACK=1 1001 5001
  • ① 的 SYN 占序号 1000；② 确认号 = x+1 = 1001（”1000 已收到，期望下一个”）
  • ③ 确认号 = y+1 = 5001，seq = x+1 = 1001（纯 ACK 不耗序号，SYN 已耗掉 1000）
  • 握手完成后 A 发数据，第一个数据字节的序号 = 1001（若③捎带数据，数据同样从 1001 编起）

验算：SYN 消耗 1 个序号：x=1000 被占用 → 数据从 1001 起 ✓

例题 2：数据传输的确认号计算

题目：连接建立后，A 向 B 发出第一个数据报文段，seq = 1，携带 100B 数据。B 正确收到后回送的确认号是多少？A 接着再发 200B，新报文段的 seq 是多少？

  • 100B 数据占用序号 1~100
  • B 的确认号 = 最后一个字节序号 + 1 = $100 + 1 = $ 101（累计确认：101 之前的字节全部收齐，无需逐个确认）
  • A 的下一个报文段 seq = 101，数据占用 101~300；B 确认 ack = 301

验算：末字节序号 = 1+100−1=100，确认号 = 100+1=101 ✓

例题 3：四次挥手的 ack = u+1 与 ack = w+1 推演

题目：A 已发送数据的最后一个字节序号为 99，随后 A 主动关闭连接；B 在半关闭期间发送了数据，其最后字节序号为 299。写出四次挥手各报文段的 seq/ack。

  • ① A 发 FIN：A 的数据占 1~99，FIN 占序号 100 → seq = u = 100，A 进入 FIN_WAIT_1
  • ② B 回 ACK：ack = u+1 = 101（确认 A 的 FIN 与此前全部数据），seq = 300，A 进入 FIN_WAIT_2
  • ③ B 发 FIN：B 的数据到 299 结束，FIN 占序号 300 → seq = w = 300，ack = u+1 = 101，B 进入 LAST_ACK
  • ④ A 回 ACK：seq = u+1 = 101（A 的 FIN 已占 100），ack = w+1 = 301（确认 B 的 FIN），A 进入 TIME_WAIT 等 2MSL

验算：两个”占序号”的报文——A 的 FIN（100）与 B 的 FIN（300）各被对方用 u+1、w+1 越过 ✓

高频考点速记

考点 记忆
TCP 五大特点 面向连接、点对点、可靠交付、全双工、面向字节流
字节流编号 按字节编号（32 位序号），不是按报文段
确认号 ack 收到的最后字节序号 + 1，对之前所有字节累计确认
首部长度 固定 20B；数据偏移以 4B 为单位，最长 60B
序号消耗 SYN、FIN 各占 1 个序号；纯 ACK 不占；连接建立后 ACK 位恒为 1
URG/PSH/RST URG 紧急插队（配紧急指针）；PSH 尽快交付；RST 复位/拒绝连接
窗口字段 通告己方接收窗口 rwnd，用于流量控制
TCP 校验和 首部+数据一起校验，加 12B 伪首部（协议 6），必须计算
三次握手 SYN(seq=x) → SYN+ACK(seq=y, ack=x+1) → ACK(seq=x+1, ack=y+1)；第三次可捎带数据
为什么三次 防失效连接请求突然到达 + 同步双方初始序号；前两次握手不能携带数据
四次挥手 FIN(seq=u) → ACK(ack=u+1) → FIN(seq=w, ack=u+1) → ACK(seq=u+1, ack=w+1)
半关闭 A→B 关闭后 B 仍可发数据；主动方停在 FIN_WAIT_2
TIME_WAIT 主动方等 2MSL：保最后 ACK 可达可重传 + 让旧报文消逝
状态归属 主动方 FIN_WAIT_1/2 → TIME_WAIT；被动方 CLOSE_WAIT → LAST_ACK
