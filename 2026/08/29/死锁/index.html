死锁

2026-08-29
  • 操作系统

死锁（Deadlock）是指多个进程互相等待对方占有的资源，且都不释放自己已占有的资源，导致所有进程都无法向前推进的僵局。它与临界资源、进程同步紧密相关，是 408 操作系统的必考模块。408 对死锁的考查集中在：死锁的概念与四个必要条件、死锁预防（破坏必要条件）、死锁避免（安全序列与银行家算法完整计算）、死锁的检测与解除，以及死锁与饥饿、死循环的辨析——其中银行家算法的大题几乎年年出现。

死锁的概念

什么是死锁

死锁：多个进程相互等待对方占有的资源，且都不释放自己已有的资源，使所有进程都被阻塞、无法向前推进。

最典型的场景：系统只有一台打印机和一台扫描仪，P1 与 P2 互相持有对方下一步需要的设备——

考点：死锁的进程全部处于阻塞态（等待的事件永远不会到来）；死锁必须依靠外部干预（剥夺资源、撤销进程）才能解除，进程自身无法走出死锁。

死锁产生的原因

原因 说明 例子
竞争不可剥夺资源 资源数量不足，多个进程争抢只能独占、不可抢走的资源 打印机等独占设备；也包括临时性资源（信号量、消息）
进程推进顺序不当 申请、释放资源的顺序非法，交叉占有形成僵局 P1 占 A 要 B 的同时 P2 占 B 要 A
信号量使用不当 P 操作顺序错误 生产者-消费者中先 P(mutex) 再 P(empty)，满时持有 mutex 等 empty

考点：资源不足只是外部条件，根本原因是进程推进顺序非法——资源充足时顺序不当也可能死锁；反之资源紧张若推进得当也未必死锁。

死锁的四个必要条件

四个条件缺一不可：任何一条不成立，死锁就不可能发生；反过来死锁发生时，四条必然同时满足。

条件 含义 能否破坏
互斥 资源一次只能被一个进程使用，其他进程必须等待 不可破坏（临界资源的固有属性）
占有并等待（请求保持） 进程已占有至少一个资源，又提出新请求，等待时不放手已有的资源 可破坏（一次性静态分配）
不可剥夺（不可抢占） 已获得的资源只能由进程自己用完后主动释放，不能被强行夺走 可破坏（剥夺式分配）
循环等待 存在等待环 P1 等 P2、P2 等 P3、……、Pn 等 P1，每个进程都在等下一家手里的资源 可破坏（顺序资源分配法）

考点：破坏四条件中的任意一个即可预防死锁；但互斥不可破坏，实际只能破坏后三个。
易错点：死锁 ⇒ 循环等待，但循环等待 ⇏ 死锁——同类资源有多个实例时，存在等待环也可能不死锁（详见”检测与解除”）；无环则必无死锁。

死锁的处理策略总览

策略 思想 起作用时机 资源利用率 吞吐量 开销
死锁预防 静态破坏必要条件之一，让死锁无法发生 事前（设计阶段） 低 低 无算法开销，但资源浪费大
死锁避免 每次分配前动态判断安全性，只在安全时分配 运行中（每次分配） 较高 较高 每次分配都要计算（银行家算法开销大）
检测与解除 放任死锁发生，定期检测，发生后解除 事后 高 高 检测开销 + 解除代价（撤销进程损失大）
鸵鸟策略 假装看不见，发生死锁后重启或人工处理 不处理 最高 最高 无

鸵鸟策略：像鸵鸟把头埋进沙子一样假定死锁发生概率极低、处理它不值得——Windows、Linux 等通用操作系统都采用，是工程上最实用的选择。

考点：四种策略的对比核心是安全性与资源利用率的权衡——限制越强越安全但利用率越低；完全不限制的鸵鸟策略利用率最高。

死锁预防

预防：通过限制进程申请资源的方式或顺序，静态地破坏四个必要条件之一，使死锁从原理上不可能发生。

破坏”请求保持”条件——静态分配

进程运行前一次性申请整个运行期所需的全部资源：满足则全程独占运行，不满足则一个也不分配、阻塞等待。

  • 变体：运行前只申请初期所需资源即可开始运行；运行中逐步释放已用完的资源，且只有在无占用时才能申请新资源
  • 优点：方法简单、实现容易、绝对保险
  • 缺点：许多资源占而不用、长期闲置，资源利用率低；进程可能长期凑不齐全部资源而饥饿

破坏”不可剥夺”条件——剥夺式分配

进程申请新资源得不到满足时，必须释放已占有的全部资源，以后需要时再重新申请。

  • 变体：由操作系统介入，从低优先级进程手中强制剥夺资源转给高优先级进程
  • 缺点：实现复杂；被剥夺进程前功尽弃（前期工作全部作废）；反复申请-释放加大系统开销，延长进程周转时间

破坏”循环等待”条件——顺序资源分配法

给系统全部资源类统一编号，规定进程只能按编号递增的顺序申请资源：想申请编号为 k 的资源时，必须已持有编号小于 k 的资源；同类多台设备也必须一次申请到位。

  • 原理：若 P1 等待 P2 的资源，必有 编号(所等资源) 严格大于 编号(所持资源)；沿等待环逐段推下去编号严格递增，绕一圈回到起点便自相矛盾 → 等待环不可能形成
  • 优点：实现简单，资源利用率和吞吐量都比静态分配高
  • 缺点：编号顺序难以恰好符合实际使用顺序；进程为遵守序提前申请暂不用的资源，造成浪费；给编程者增加不便

死锁预防策略对比

破坏的条件 做法 优点 缺点
互斥 无法破坏——临界资源必须互斥使用（SPOOLing 化只是缓解，不算破坏互斥） — 临界资源固有属性
请求保持 一次性静态分配全部资源（或用完再申请新的） 简单、保险 资源浪费、利用率低、可能饥饿
不可剥夺 申请不到新资源就释放已占有的全部资源（或 OS 强制剥夺） 无死锁、利用率相对较高 实现复杂、前功尽弃、开销大
循环等待 资源统一编号 + 递增申请（顺序资源分配法） 简单、利用率与吞吐量较高 编号难定、编程不便、可能提前申请占而不用

考点：预防是静态策略，共同代价是资源利用率下降；要能对号入座——静态分配破坏请求保持、剥夺式分配破坏不可剥夺、有序申请破坏循环等待。

死锁避免

避免：不事先加以限制，而是在每次资源动态分配前判断”分配之后系统是否仍然安全”，只在安全时才真正分配——典型动态策略，代表算法是银行家算法。

安全状态与安全序列

  • 安全序列：一个进程排列 ⟨P1​,P2​,…,Pn​⟩，按此顺序执行时，每个进程都能获得尚缺的资源并顺利运行完成（完成后归还全部资源，供后面的进程使用）
  • 安全状态：系统中至少存在一个安全序列
  • 不安全状态：找不到任何安全序列

考点：安全 ⇒ 无死锁，但不安全 ⇏ 死锁——不安全只说明”找不到保证人人完成的执行顺序”，可能死锁而非一定死锁。银行家算法”宁可信其有”：判为不安全就拒绝分配。
易错点：安全序列不唯一，判断系统是否安全只需找出任意一条安全序列即可；存在安全序列的系统中仍可能有进程暂时阻塞等待。

银行家算法

思想：像银行家放贷——已知每位客户的最大借款额，放贷前先试探性地把钱借出去，检查是否存在某种顺序让所有客户都能周转开并还清贷款；找不到就不放这笔款。

数据结构（n 个进程、m 类资源）：

结构 规模 含义
Available[j] m 当前可用的第 j 类资源数
Max[i][j] n×m 进程 i 对第 j 类资源的最大需求
Allocation[i][j] n×m 进程 i 已分得的第 j 类资源数
Need[i][j] n×m 进程 i 还需要的资源数，Need=Max−Allocation

处理进程 i 的请求 Requesti​ 的三个步骤：

  1. Requesti​≤Needi​？不成立则出错（申请量超过了它申报的最大需求）
  2. Requesti​≤Available？不成立则可用资源不足，进程阻塞等待
  3. 试探分配：Available 减去 Requesti​、Allocation 加上 Requesti​、Need 减去 Requesti​，随后做安全性检查——仍存在安全序列才正式分配；否则回滚试探、让进程等待

例题：寻找安全序列

系统有 5 个进程、3 类资源 A/B/C，资源总量 (10, 5, 7)，某时刻状态如下：

进程 Max (A B C) Allocation (A B C) Need (A B C)
P0 7 5 3 0 1 0 7 4 3
P1 3 2 2 2 0 0 1 2 2
P2 9 0 2 3 0 2 6 0 0
P3 2 2 2 2 1 1 0 1 1
P4 4 3 3 0 0 2 4 3 1

第一步：求 Available。已分配合计 = (0+2+3+2+0, 1+0+0+1+0, 0+0+2+1+2) = (7, 2, 5)，故 Available=(10,5,7)−(7,2,5)=(3,3,2)。

第二步：逐步找安全序列。取 Work = Available；每轮找一个 Need ≤ Work 的未完成进程，令其完成并回收全部 Allocation（Work += Allocation），直到所有进程完成或无进程可选。

步骤 判断 Need ≤ Work 回收 Allocation 新 Work
初始 Work = (3,3,2)；P0：Need (7,4,3) > (3,3,2) ✗ — (3,3,2)
① 选 P1 Need (1,2,2) ≤ (3,3,2) ✓ + (2,0,0) (5,3,2)
② 选 P3 Need (0,1,1) ≤ (5,3,2) ✓ + (2,1,1) (7,4,3)
③ 选 P4 Need (4,3,1) ≤ (7,4,3) ✓ + (0,0,2) (7,4,5)
④ 选 P0 Need (7,4,3) ≤ (7,4,5) ✓ + (0,1,0) (7,5,5)
⑤ 选 P2 Need (6,0,0) ≤ (7,5,5) ✓ + (3,0,2) (10,5,7)

验算：最终 Work = (10,5,7)，恰等于资源总量，全部进程完成 ✓

结论：存在安全序列 P1 → P3 → P4 → P0 → P2（安全序列不唯一，如 P1 → P3 → P0 → P2 → P4 同样可行），系统当前处于安全状态。

例题：请求向量能否满足

问：此刻 P1 发出请求 Request1​=(1,0,2)，系统能否分配？

三步判断：

  1. (1,0,2)≤Need1​=(1,2,2) ✓（未超过 P1 申报的最大需求）
  2. (1,0,2)≤Available=(3,3,2) ✓（系统有足够可用资源）
  3. 试探分配：Available = (3,3,2) − (1,0,2) = (2,3,0)；P1 的 Allocation 变为 (2,0,0) + (1,0,2) = (3,0,2)；P1 的 Need 变为 (1,2,2) − (1,0,2) = (0,2,0)

对新状态做安全性检查（方法同上）：

步骤 判断 Need ≤ Work 回收 Allocation 新 Work
初始 Work = (2,3,0)；P0：Need (7,4,3) > (2,3,0) ✗ — (2,3,0)
① 选 P1 Need (0,2,0) ≤ (2,3,0) ✓ + (3,0,2) (5,3,2)
② 选 P3 Need (0,1,1) ≤ (5,3,2) ✓ + (2,1,1) (7,4,3)
③ 选 P4 Need (4,3,1) ≤ (7,4,3) ✓ + (0,0,2) (7,4,5)
④ 选 P0 Need (7,4,3) ≤ (7,4,5) ✓ + (0,1,0) (7,5,5)
⑤ 选 P2 Need (6,0,0) ≤ (7,5,5) ✓ + (3,0,2) (10,5,7)

安全序列 P1 → P3 → P4 → P0 → P2 依然存在 → 分配后系统仍安全 → 正式分配，批准 P1 的请求。

再追问两问（速判，接上一步之后的最新状态）：

  • P4 请求 (3,3,0)：(3,3,0)≤Available=(2,3,0)？A 类 3 > 2 ✗ → 可用资源不足，P4 阻塞等待（无需试探，更谈不上安全性检查）
  • P0 请求 (0,2,0)：两个不等式均满足；试探后 Available = (2,1,0)、P0 的 Need = (7,2,3)。逐一检查：P0 (7,2,3)、P1 (0,2,0)、P2 (6,0,0)、P3 (0,1,1)、P4 (4,3,1) 的 Need 全部大于 Work (2,1,0) → 找不到任何安全序列 → 不安全 → 拒绝分配（回滚，让 P0 等待）

考点：银行家算法大题的标准答题模板——先验证 Requesti​≤Needi​ 与 Requesti​≤Available 两个不等式，再试探分配、最后做安全性检查；检查失败必须回滚数据再下结论。
易错点：判为”不安全而拒绝”时，系统并未死锁——不安全只是”不能保证不死锁”，银行家算法采取保守策略防患于未然。

死锁的检测与解除

检测解除：不做任何限制，允许死锁发生；系统定期运行检测算法判断当前是否死锁，一旦发现便设法解除。适用于死锁不常发生的系统，资源利用率最高，但检测与解除都有开销。

资源分配图

资源分配图是描述系统资源分配状态的有向图，用它可直观判断死锁：

  • 进程结点：圆圈，标注进程名（P1、P2……）
  • 资源结点：方框，标注资源名；框内圆点数 = 该类资源的实例数
  • 请求边：P → R（从进程指向资源框），表示该进程正在申请一个该类资源
  • 分配边：R → P（从资源框指向进程），表示该类资源的一个实例已分配给该进程

易错点：两类边的箭头方向相反——请求边”进程指资源”，分配边”资源指进程”；读图时先数清每类资源的实例数再判断环。

死锁定理与图化简

死锁定理：资源分配图无环 → 一定无死锁；有环 → 不一定死锁：

环中资源实例情况 有环时的结论
每类资源只有 1 个实例 一定死锁（环上进程互卡、无实例可释放）
存在多个实例的资源 可能死锁，也可能不死锁，须化简后判断

图化简：找一个非孤立且所有请求边都能立即满足的进程，删去它的全部请求边与分配边（相当于让它运行完成并归还资源），回收后再继续化简其他进程；若最终全部边都可删除（图可完全化简）→ 无死锁；若最后残留无法化简的子图 → 该子图中的进程陷入死锁。

含环辨析小例（方框内为资源及其实例数）：

易错点：判断”有环是否死锁”先看实例数——单实例有环必死锁；多实例有环须化简；无环必无死锁是可秒答的判断题。

检测算法与时机

检测算法（思路与银行家安全性检查一致，只是把 Need 换成已发出且尚未满足的请求矩阵 Request）：

  1. Work = Available；全部进程置 Finish[i] = false（Allocation[i] 全零者可直接置 true）
  2. 寻找 Finish[i] = false 且 Requesti​≤Work 的进程：视其可以完成，置 Finish[i] = true，并回收资源 Work += Allocation[i]，返回第 2 步
  3. 算法结束时仍有 Finish[i] = false 的进程 → 这些进程即处于死锁状态

检测时机：进程申请资源得不到满足时立刻检测（及时但开销大）；定时（周期性）检测；或当CPU 利用率骤降、疑似死锁时触发检测。

死锁的解除

方法 做法 特点
资源剥夺法 从若干死锁进程中强行剥夺足够的资源，分给其余死锁进程 被剥夺者前功尽弃，还要防止它再次死锁
撤销进程法 逐个撤销死锁进程（按优先级、已运行时间、代价最小原则挑选），直至死锁解除；或一次性撤销全部死锁进程 强制撤销会丢失已完成的部分工作，代价可能很大
进程回退法 让一个或多个死锁进程回退到足以回避死锁的某个历史检查点重新执行 系统必须保存历史信息与检查点，开销大

考点：检测解除的完整流程 = 图化简发现死锁 → 挑选”代价最小”的进程剥夺资源或撤销；”逐个撤销、代价最小”是选择题高频表述。

死锁、饥饿与死循环的辨析

对比项 死锁 饥饿 死循环
本质 多进程互相等待对方的资源 进程长期得不到资源（或 CPU）而无法推进 程序逻辑错误，跳不出循环
涉及进程数 至少两个且互相等待 一个进程也可饥饿 一个进程即可发生
进程状态 全部处于阻塞态 可能阻塞（等 I/O），也可能就绪（排队等 CPU） 处于运行态
产生原因 竞争资源 + 推进顺序非法（操作系统层面） 分配策略不公（如短进程优先、静态优先级） 程序员代码写错（与操作系统无关）
能否自行解除 不能，必须外部干预 可能，等待久了自然缓解（如老化提高优先级） 不能，需人工干预

考点：三者都表现为”进程无法推进”，抓住两点区分——进程数（死锁至少两个且互相等待）与进程状态（死锁在阻塞、死循环在运行）；死锁一定伴随饥饿，饥饿未必是死锁。
易错点：饥饿进程可能正躺在就绪队列里，只是轮不上处理机；而死锁进程的等待事件永远不会到来。

高频考点速记

考点 记忆
死锁定义 多进程互相等待对方资源且不释放，全部阻塞、无法推进，需外部干预
产生原因 竞争不可剥夺资源（含临时资源）+ 进程推进顺序非法（信号量误用）
四必要条件 互斥、占有并等待、不可剥夺、循环等待，缺一不可；互斥不可破坏，预防只能破坏其余三个
破坏请求保持 一次性静态分配全部资源——简单保险，但浪费、利用率低、可能饥饿
破坏不可剥夺 申请不到新资源就释放已占有的全部——实现复杂、前功尽弃
破坏循环等待 资源统一编号、递增申请——利用率较高，但编号难定、编程不便
安全状态 存在安全序列 ⇒ 必无死锁；不安全 ⇏ 死锁（只是有可能）
银行家数据结构 Need=Max−Allocation；请求须满足 Requesti​≤Needi​ 且 Requesti​≤Available
银行家算法流程 两不等式 → 试探分配 → 安全性检查，失败则回滚让进程等待
安全性检查 每轮找 Need≤Work 的进程，回收后 Work += Allocation，全部完成即安全
死锁定理 无环必无死锁；单实例有环必死锁；多实例有环须化简判断
检测与解除 放任发生 + 定期检测（图化简）；解除用剥夺资源 / 撤销进程 / 进程回退
死锁 vs 饥饿 死锁 ≥2 进程互等、全阻塞、需外力；饥饿 1 进程即可、可能就绪、可自行缓解
鸵鸟策略 假装不处理、利用率最高，死锁了就重启；Windows / Linux 采用
